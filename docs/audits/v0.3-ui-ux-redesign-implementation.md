# Keep It Up: UX Simplification and Commitment Model

## Purpose

Refine Keep It Up around one central promise:

**Help people keep the commitments they make to themselves.**

Make it easy to choose a commitment, understand what doing it means, complete it, and return tomorrow. Avoid turning the product into a comprehensive fitness tracker, notes app, or task manager.

Inspect the existing application before implementation. Reuse working components and patterns where sensible, and avoid unnecessary rewrites.

## 1. Product terminology

Use these concepts consistently:

- **Commitment:** An individual thing the user intends to do or avoid.
- **Activity:** The action associated with a commitment, such as reading, running, or journaling.
- **Path:** A ready-made collection of commitments that can be added together (for example, *Arnold* or *The Carpenter*).
- **Routine:** A user-defined grouping of multiple commitments, such as a morning or evening routine.

Prefer user-facing language such as “Add a commitment”, “Build a habit”, “Break a habit”, and “Explore paths”. Do not call every individual commitment a routine.

## 2. Replace the multi-step creation wizard with one screen

### Screen structure

**Heading:** “What would you like to commit to?”

1. **Search/create input**
   - Let users search for a suggested activity or enter their own.
   - Example placeholder: “Search or create a commitment…”
   - Selecting a suggestion should populate/select it in the composer, not launch another wizard.
   - Support custom commitment titles.

2. **Two modes**
   - **Build a habit:** positive actions the user wants to do.
   - **Break a habit:** behaviours the user wants to avoid.

3. **Categorised suggested activities**
   - Organise suggestions into meaningful categories, not one undifferentiated list.
   - Preserve or improve the existing category structure where appropriate.
   - Possible Build categories: Movement, Mindfulness, Learning, Personal growth, Faith, Relationships, Self-care.
   - Possible Break categories: Alcohol, Smoking, Food, Screen time, Procrastination.
   - Categories must be easy to browse on mobile.
   - Selecting a category filters suggestions.
   - Search works across suggestions and categories.
   - Use progressive disclosure; do not overwhelm users with every suggestion at once.

4. **Frequency/schedule**
   - Provide quick choices such as Daily, 3 times per week, and Custom.
   - Reuse existing scheduling capabilities.
   - Do not force users through a separate schedule wizard.
   - Make the selected schedule clear before saving.

5. **Primary action:** “Add commitment”.

### Ready-made paths on the same screen

Paths are shortcuts for adding multiple commitments, not a third type of individual activity.

- Show a distinct section below individual activity suggestions, such as “Looking for inspiration? Start with a ready-made path.”
- Include existing paths, such as **Arnold** and **The Carpenter**, with concise descriptions.
- Each path has an **Explore** action.
- Exploring expands its details inline on the same screen. Do not open another wizard.
- Show included commitments, their instructions, and relevant schedules.
- Provide an **Add this path** action.
- Add the included commitments together with clear confirmation and no unexpected extra steps.
- Handle duplicates predictably. Do not silently create duplicate commitments; explain what happened.

## 3. Binary completion is the default

The default completion model for commitments is:

- **Done**
- **Not done**

A user should be able to complete an ordinary commitment with one interaction. Do not require duration, distance, quantity, or other numeric input just to mark it complete.

Examples:
- Listen to calming sounds.
- Write down worries.
- Name one good quality being developed.
- Write three things to be grateful for.
- Read a chapter.
- Go running.
- Avoid alcohol.
- Avoid social media.

The title and instruction communicate what the user promised to do. The completion interaction remains consistent across activity types.

### Optional measurements

Do not remove useful measurement functionality outright. Make it optional and secondary.

- Optional targets and actual measurements may be available for users who want them.
- A user must still be able to complete a commitment without entering a measurement.
- Never automatically send users to a numeric-entry screen when they tap a commitment.
- Make optional tracking clear before the activity starts and keep simple completion prominent.
- Preserve existing measurement capabilities where they provide genuine value, but do not let them dictate default UX.

Examples:
- Running: default Done; optional distance target/recording.
- Reading: default Done; optional pages target/recording.
- Meditation: default Done; optional duration/timer.
- Strength workout: default Done; optional detailed workout tracking.

## 4. Separate commitment, instruction, and completion

Represent three distinct concepts in the data and UI:

1. **Commitment title:** What the user is committing to.
2. **Instruction:** What the user should actually do.
3. **Completion method:** How the user records that they did it.

Instructions must match the experience the app provides.

| Commitment | Instruction | Default completion |
|---|---|---|
| Gratitude journaling | Write down three things you're grateful for today. | Done |
| Calming sounds | Spend a few minutes listening to calming sounds. | Done |
| Reflection | Think about one thing you did well today. | Done |
| Running | Go for a run. | Done |
| No alcohol | Avoid alcohol today. | Done / Not done |

Use clear action verbs. Avoid implying that the app provides a tool or workspace when it does not.

### Lightweight optional notes

- Support optional notes where they add value, without turning Keep It Up into a notes application.
- For journaling, prayer, or reflection, a lightweight optional text field may be useful.
- Do not require users to write inside Keep It Up if the commitment can reasonably be completed elsewhere.
- Do not imply the app provides a journaling workspace unless it actually does.
- No rich-text editor, folders, tagging system, or general-purpose note management.

For example, “Write down three things you're grateful for today” must not open a screen that only asks for minutes. Either offer a lightweight way to record the entries or let the user mark it done after completing it elsewhere. Make the choice clear.

## 5. Specialised activity tracking

Keep detailed tracking optional, not the defining experience.

### Physical exercise

- Preserve the specialised gym exercise capability if useful.
- Exercise name, sets, reps, and weight are optional details.
- A user who simply wants to commit to “Complete a strength workout” can add and complete it without configuring exercises.
- Do not make the gym-specific configuration screen mandatory in the general commitment flow.
- If detailed workout configuration remains, reveal it only when relevant and clearly label it optional/advanced.
- Do not force other activity types through a gym-style configuration model.

### Negative commitments

For “Break a habit” commitments (for example, no alcohol or no smoking):
- Keep interaction simple: record whether the user stayed on track.
- Avoid shame, guilt, red warning states, or language that treats a slip as personal failure.
- A missed commitment is information, not a reason to punish the user.

## 6. Home screen and daily completion

Make today's commitments the centre of the home screen. Users should immediately understand:
- What they committed to today.
- What they have completed.
- What remains.

### Commitment cards

- Keep cards simple and scannable.
- Show the commitment title and, where useful, its concise instruction.
- Provide a clear completion control.
- Avoid overloading cards with statistics, measurements, or secondary metadata.

### Completing a commitment

1. User taps the completion control.
2. Show brief positive feedback (for example, a small congratulatory ribbon or confirmation animation).
3. Update the daily progress indicator.
4. Remove the completed card from the active “to do today” list.
5. Keep the completed commitment accessible in History or a completed-items view.
6. Provide a short-lived Undo action for accidental completion.

The card disappears from the active list, but the underlying commitment and completion record are not deleted.

- Keep animations brief and non-disruptive.
- Respect reduced-motion preferences.
- Ensure completion is understandable without animation.
- Avoid excessive celebrations that become irritating with repetition.

### Progress

- Retain a simple daily progress indicator and make its meaning obvious.
- Make completed commitments accessible without leaving them cluttering the active list.
- Keep progress summaries useful and restrained.
- Avoid turning the home screen into a dense analytics dashboard.

## 7. Encourage return without punishment

- Do not punish missed days.
- Avoid broken-streak warnings, shame-based messages, or aggressive red error states.
- Do not imply one missed day invalidates previous progress.
- Use supportive, neutral language when users return after missing commitments.
- Example: “Yesterday didn't go as planned. That's okay. Here's today.”
- Positive feedback should acknowledge effort without becoming childish or excessive.
- Consider a gentle end-of-day transition that acknowledges completed commitments and presents the next day's commitments.

The goal is a small, positive daily ritual, not another source of pressure.

## 8. Mobile interactions and accessibility

- Keep the existing web app/PWA. Do not propose a native rewrite just to support familiar mobile interactions.
- Support swipe-to-reveal Edit and Delete on touch devices where appropriate.
- Swipe must not be the only way to access these actions. Provide accessible alternatives for keyboard, pointer, and assistive-technology users.
- Use appropriate touch targets and clear focus states.
- Avoid accidental destructive actions; confirm or provide Undo for deletion.
- Ensure creation and completion work on narrow mobile screens and larger screens.
- Preserve the visual identity unless a change is needed for clarity or usability.

## 9. Data model and migration

Inspect the current schema, persistence layer, and existing user data before changing the model.

The conceptual model should support:
- Individual commitments.
- Build/break commitment types.
- Instructions separate from titles.
- Frequency/scheduling.
- Optional targets and measurements.
- Optional lightweight notes.
- Optional specialised configuration (such as detailed gym exercises).
- Ready-made paths containing multiple commitments.
- User-defined grouped routines (such as morning/evening routines), where supported.
- Completion history independent of the active home-screen list.

Do not perform a destructive migration. Preserve existing commitments, schedules, workout details, and completion history. Provide a safe migration or backward-compatible mapping if the current model differs.

Do not add unnecessary backend services or external dependencies. Preserve offline/PWA behaviour.

## 10. Implementation workflow

Work in small, sequential stages. Do not attempt a broad redesign in one uncontrolled pass.

### Stage 1: Inspect and map

- Run the application and inspect the actual UI.
- Map the current creation, home, completion, paths, schedules, and persistence flows.
- Identify reusable components and behaviours.
- Report the implementation sequence and data migration risks before structural changes.

### Stage 2: Simplify creation

- Implement the single-screen creation experience.
- Include Build a habit / Break a habit modes.
- Include categorised suggestions and search.
- Include inline path exploration and adding.
- Include simple frequency selection.
- Selecting a suggestion must not unexpectedly navigate to another wizard.
- Keep activity-specific configuration optional and conditional.

### Stage 3: Simplify completion

- Make binary completion the default for all commitments.
- Remove mandatory numeric-entry screens from the normal completion journey.
- Preserve optional measurement and specialised workout functionality.
- Ensure instructions accurately describe what users need to do.
- Add lightweight optional notes only where useful and consistent with the architecture.

### Stage 4: Improve home feedback

- Update commitment cards and daily progress.
- Implement completion feedback, removal from the active list, History access, and Undo.
- Add restrained positive messaging.
- Ensure missed days are handled without punishment.

### Stage 5: Mobile and accessibility

- Add swipe-to-edit/delete where appropriate, with accessible alternatives.
- Verify responsive layouts, keyboard navigation, focus states, touch targets, and reduced-motion behaviour.

### Stage 6: Verify actual user journeys

Test these flows in the running application:

1. Create a custom positive commitment.
2. Add a suggested positive commitment from a category.
3. Add a negative commitment.
4. Search for a suggested activity.
5. Set a daily schedule.
6. Set a custom/weekly schedule.
7. Explore a ready-made path inline and add it.
8. Add a path containing an existing commitment.
9. Complete an ordinary commitment with one interaction and no numeric input.
10. Undo an accidental completion.
11. Find a completed commitment in History.
12. Complete a journaling commitment without being misled into a duration-only screen.
13. Add and complete a basic strength-workout commitment without configuring exercises.
14. Use optional detailed workout tracking.
15. Return after missing a day and verify the experience is supportive.
16. Use creation and completion on mobile and desktop.
17. Verify offline/PWA behaviour and persistence.

Fix observed UX defects rather than merely adding tests that encode the current implementation.

## Non-goals and constraints

- Do not turn Keep It Up into a full fitness application.
- Do not turn it into a general-purpose notes application.
- Do not require numerical measurement to complete commitments.
- Do not add elaborate gamification, excessive statistics, or guilt-based streak mechanics.
- Do not rebuild the application as a native app.
- Do not introduce unnecessary dependencies or services.
- Do not discard useful functionality or user data without a migration plan.
- Do not assume passing tests prove the UX is good. Validate real user journeys in the running application.

## Product principle

**Keep It Up should help people fulfil the commitments they make to themselves, then help them stay accountable.**

Every screen and interaction should make that easier.
