# Keep It Up — Consolidated UI/UX Implementation Tasks

## Objective

Improve the Keep It Up app's current main screens based on the latest UI/UX audit.

The main goal is to make the product clearer, more coherent, and easier to use without redesigning the application from scratch.

The most important architectural UX decision is:

> **Today is for today's actions. Progress is for historical trends. Review is for reflection and plan adjustment. History is for past sessions.**

Preserve the existing visual identity, design tokens, components, data model, and overall minimalist aesthetic wherever possible.

Do not introduce unrelated features.

---

# 1. Today Screen — Redesign Around Today's Activities

## 1.1 Remove analytics from Today

Remove these sections from Today:

- Momentum
- Overall consistency
- This Week
- Weekly goal statistics
- Other historical/multi-day metrics

These belong elsewhere:

### Progress
- consistency
- 7 / 30 / 90 day trends
- totals
- volume
- duration
- historical performance

### Review
- weekly performance
- missed activities
- areas of difficulty
- successes
- plan adjustment

Today should answer:

> **What do I need to do today, and how much have I completed?**

---

## 1.2 New Today structure

Use this conceptual structure:

```text
Thursday, 8 October

3 of 5 completed
━━━━━━━━━━━━░░░░░░

TODAY'S ACTIVITIES

✓ Journaling
  Completed

✓ Go outside
  Completed

○ Read
  ~10 min
  [ Start ]

○ Strength workout
  ~30 min
  [ Start ]

○ Meditation
  ~5 min
  [ Start ]
```

The exact visual implementation should use existing design-system components.

---

## 1.3 Date header

Display the current date prominently at the top.

Example:

```text
Thursday, 8 October
```

Use existing date-formatting conventions.

Do not add unnecessary controls beside the date.

---

## 1.4 Daily completion summary

Immediately below the date show:

```text
3 of 5 completed
```

plus a compact visual progress indicator.

Examples:

```text
0 of 5 completed
```

```text
3 of 5 completed
```

```text
5 of 5 completed
```

The metric must be based on today's planned activities.

Do not use the historical `67% consistency` metric here.

When all activities are complete, clearly communicate the completed state.

---

# 2. Today's Activity List

## 2.1 Activities are the dominant content

Use:

```text
TODAY'S ACTIVITIES
```

as the main section.

Each activity should be easy to scan and should clearly communicate:

- activity name
- completion state
- estimated duration where available
- primary action if incomplete
- secondary actions if already completed

---

## 2.2 Activity ordering

Do not simply display activities in creation order.

Use this sorting strategy:

1. Preferred time
2. Estimated duration
3. Stable original order as final tie-breaker

Preferred-time categories:

```text
Morning
Afternoon
Evening
Any time
```

Do not introduce precise calendar scheduling.

Preferred time is an ordering/preference mechanism.

---

## 2.3 Quick wins / effort

Do **not** introduce arbitrary effort weights such as:

```text
Journaling = 2
Reading = 4
Workout = 8
```

For the MVP, estimated duration is a much simpler and more explainable proxy for quick wins.

When activities have the same preferred-time category, shorter activities should appear before longer ones.

If the existing data model already contains duration information, reuse it.

If it does not, inspect the existing model before introducing new fields.

---

# 3. Incomplete Activity State

An incomplete activity should make it immediately obvious that the user still needs to do it.

Example:

```text
○ Strength workout
  ~30 min

  [ Start ]
```

Requirements:

- activity name has strongest hierarchy
- duration is secondary
- Start is the primary action
- use the existing primary button style
- do not make secondary controls compete with Start

---

# 4. Completed Activity State

Completed activities should remain visible on Today.

Example:

```text
✓ Journaling
  Completed
```

Requirements:

- completed state must be obvious
- completed activity must not look like an unfinished task
- use existing success/status styling where appropriate
- completed activities remain in the list so the user can see what they accomplished

---

# 5. "Log another"

If the existing application supports logging another session for an activity already completed today, retain it.

However:

> `Log another` must be visually secondary.

Example:

```text
✓ Strength workout
  Completed

  Log another
```

It should not look equivalent to the primary `Start` action.

---

# 6. Today Empty and Complete States

## No activities today

Do not leave the screen looking broken or empty.

Provide a concise empty state, for example:

```text
No activities planned for today.

Enjoy the day, or add an activity to your plan.
```

Use existing terminology and available actions.

## Everything completed

Show the completion summary clearly:

```text
5 of 5 completed
━━━━━━━━━━━━━━━━━━
```

Keep all completed activities visible.

Do not add large celebration animations or unrelated motivational content.

---

# 7. Today Screen: Remove Unnecessary Content

Do not add:

- motivational quotes
- generic encouragement blocks
- large illustrations
- weekly summaries
- streak statistics
- historical charts
- Momentum
- This Week
- large dashboard-style analytics

The screen should feel like a focused daily action list.

---

# 8. Global State / Data Consistency

## 8.1 Fix the "Missed yesterday?" banner

The current banner can remain visible even after today's activities are completed.

It should only appear when it is actually useful.

Requirements:

- show it when there is genuinely a missed session from yesterday and today's state makes the message useful
- hide it when all relevant today's actions are already complete
- do not make the user feel that a completed day is still unfinished

Do not hard-code the state.

---

## 8.2 Consistency calculations

The current UI shows inconsistent percentages, e.g. values around 13% versus `1 / 7`.

Establish one source of truth for consistency calculations.

Example:

```text
1 / 7 = 14.3% → display 14%
```

Today, Progress, and Review must use the same calculation and rounding rules.

Do not implement separate calculations per screen.

Inspect the existing implementation before changing the calculation logic.

---

# 9. History Screen

## 9.1 Make history items clearly interactive

History entries should clearly look tappable/openable.

Possible approaches:

- entire row/card is tappable
- subtle chevron
- hover/pressed state
- appropriate cursor on desktop

Do not add unnecessary UI if a strong interactive row state is sufficient.

---

## 9.2 Standardise "activity" vs "session"

The History screen currently uses terminology such as:

> 1 activity

Prefer `session` where the item represents a recorded session.

Establish consistent domain terminology.

Suggested terminology:

| Concept | Preferred term |
|---|---|
| User-defined thing they want to do | Goal |
| Planned occurrence | Activity/session |
| Recorded occurrence | Session / Log |
| Completion state | Completed |
| Historical records | Sessions |
| Long-term success metric | Consistency |
| Configuration change | Edit / Adjust |

Do not blindly rename concepts without inspecting the actual domain model.

---

## 9.3 Improve History information hierarchy

Make the most important information easiest to scan:

```text
Strength workout              Done
1 session                     10 kg × 3
```

Goal/activity name and completion state should be stronger than metadata.

---

# 10. History Detail Panel

Improve the detail view hierarchy.

Conceptual structure:

```text
8 October                         [×]

Strength workout

Set 1   10 kg × 3
Set 2   10 kg × 4
Set 3   10 kg × 5

Volume                         120 kg
```

Requirements:

- clear date
- clear session/activity title
- clear set information
- clear totals
- avoid unnecessary duplicated labels
- close control has a proper touch target and accessible label

Responsive behaviour:

- desktop/tablet: side drawer is acceptable
- narrow mobile: use bottom sheet or full-screen detail view if needed

---

# 11. Progress Screen

## 11.1 Remove accidental emptiness

The Progress screen currently has a large amount of unused space.

Do not fill it with decorative content just to occupy space.

Instead:

- tighten the layout
- improve useful information grouping
- allow intentional whitespace
- only add existing/product-relevant information

---

## 11.2 Fix progress percentage consistency

Progress values must use the same calculation and rounding rules as Today and Review.

For example:

```text
1 / 7 → 14%
```

Do not independently calculate progress percentages per screen.

---

## 11.3 Improve progress bars

Progress bars should be readable at a glance.

Current bars are too subtle.

Improve:

- track visibility
- fill visibility
- relationship between percentage and bar

Keep them visually subordinate to the actual data.

---

## 11.4 Time-range selector

For:

```text
7 days
30 days
90 days
```

ensure:

- active selection is obvious
- inactive options remain readable
- controls are easy to tap
- selected state does not rely solely on colour

---

## 11.5 Clarify totals

Current totals such as:

```text
Volume
120 kg

Duration
1h 5m
```

need to clearly correspond to the selected time range.

For example:

```text
TOTALS · LAST 7 DAYS

Volume       120 kg
Duration     1h 5m
```

Use the actual selected range dynamically.

---

# 12. Weekly Review Screen

## 12.1 Show the review date range

`Your week` is too ambiguous.

Show the actual period.

Example:

```text
Your week
5 Oct – 11 Oct
```

Use existing date conventions.

---

## 12.2 Improve negative framing

Avoid overly punitive language such as:

> WHERE YOU STRUGGLED

and presenting missed sessions without context.

The app should be honest about missed activities while remaining constructive.

Possible direction:

```text
This week

18 planned sessions were missed.

Go outside was the hardest goal to keep up.
```

Use appropriate copy based on actual data.

---

## 12.3 Explain missed-session denominators

If the UI says:

```text
18 planned sessions missed
```

make the total planned count understandable.

For example:

```text
3 of 21 planned sessions completed
18 missed
```

The user should not have to reverse-engineer where the number came from.

---

## 12.4 Clarify Momentum if retained on Review

If a metric such as:

```text
3 of 126 planned sessions completed
```

is retained, clearly explain what period the 126 sessions represents.

Do not show a large unexplained denominator.

If the metric is all-time, label it as such.

---

## 12.5 Plan actions

For:

```text
Keep my plan
Adjust my plan
```

make the hierarchy clear.

Recommended:

- `Keep my plan` → primary
- `Adjust my plan` → secondary

Add a short contextual explanation only if needed.

Do not create a large explanatory block.

---

# 13. Global Accessibility / Interaction

## 13.1 Secondary text contrast

Many metadata labels are too pale.

Review:

- last-session metadata
- goal metadata
- History metadata
- percentages
- helper text
- secondary navigation text

Improve contrast while retaining hierarchy.

Use:

- size
- weight
- spacing
- grouping

rather than insufficient contrast to make secondary content look secondary.

---

## 13.2 Touch targets

Audit all interactive elements.

Aim for approximately 44x44px touch targets, especially:

- edit icons
- close buttons
- header add button
- bottom navigation
- tabs
- list rows

The visible icon can remain small; the interactive hit area should be comfortable.

---

## 13.3 Bottom navigation

Keep:

```text
Today
History
Progress
Review
```

Requirements:

- readable labels
- clear selected state
- consistent icon sizing
- comfortable touch targets
- fixed/stable positioning
- no overlap with scrollable content
- appropriate mobile safe-area padding

Do not change the information architecture.

---

# 14. Global Button Hierarchy

Establish consistent action hierarchy.

## Primary

Orange filled button.

Use for:

- Start session/activity
- Keep my plan where it is the recommended action

## Secondary

Outlined/light button.

Use for:

- Adjust my plan
- Log another

## Tertiary

Text/icon action.

Use for:

- edit
- close
- low-priority controls

Do not make secondary actions visually compete with primary actions.

---

# 15. Visual Polish

## 15.1 Reduce excessive card nesting

The app currently uses many bordered cards.

Do not remove all cards.

Instead:

- reserve cards for meaningful grouping
- use whitespace where it communicates grouping better
- avoid unnecessary bordered containers inside bordered containers

Keep the minimalist visual direction.

---

## 15.2 Improve vertical rhythm

Review spacing between:

- page title and contextual messages
- contextual messages and activity list
- activity list and other sections
- section titles and content
- Progress sections
- Review sections

Use a consistent spacing scale.

---

Standardise terminology throughout the application.

Suggested vocabulary:

| Concept | Preferred term |

| Something planned for today | Activity |
| Recorded completion | Session |
| Recording a session | Log |

Use a coherent date system across:

# Final UX principle

Keep It Up should not try to make every screen do everything.

The product should have a clear mental model:

```text
TODAY
What do I need to do?

HISTORY
What have I done?

PROGRESS
How am I doing over time?

REVIEW
How did I do, and should I change my plan?
```

When implementing these changes, optimise for **clarity, focus, consistency, and low cognitive load** rather than adding more information to the interface.
